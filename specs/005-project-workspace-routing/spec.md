# 功能规格说明：项目空间隔离与路由

**功能分支**: `005-project-workspace-routing`  
**创建时间**: 2026-03-13  
**状态**: 草稿  
**输入**: 用户描述: “在 `.clawx` 目录下设计并落地项目隔离策略，明确 `/project` 与 `/new` 语义、同一 bot 并发多项目时的隔离方式，并与现有 channel/window/session 体系对齐。”

## Clarifications

### Session 2026-03-13

- Q: 这个能力是否应独立成新 feature？ → A: 是，独立为 Phase 5。
- Q: `/new` 是否负责创建新项目？ → A: 不是，`/new` 只在“当前项目”内创建新会话。
- Q: 同一 bot 同时做两个项目如何隔离？ → A: 通过 route key 绑定到不同项目，默认不共享 workspace。
- Q: 意图识别命中另一个项目时是否自动切换？ → A: 不自动切，先给出切换建议并等待确认。

## 用户场景与测试（必填）

### 用户故事 1 - 显式管理项目并绑定工作空间（优先级：P1）

作为运维/开发者，我希望可以显式创建、查看、切换项目，并让每个项目对应独立 workspace，这样同一 bot 下的任务不会互相污染代码与上下文。

**为什么是这个优先级**: 这是项目隔离的主路径，没有它就无法保证可控隔离。

**独立测试方式**: 通过 `/project create|list|use|current` 完成两个项目初始化，验证不同项目写入不同目录，切换后 `/new` 在当前项目生效。

**验收场景**:

1. **假如** 用户执行 `/project create bid`，**当** 创建成功时，**那么** 系统应生成 `~/.clawx/workspaces/bid` 并登记项目元数据。
2. **假如** 用户在同一窗口执行 `/project use bid`，**当** 后续执行 `/new`，**那么** 新会话应绑定 `bid` 项目而非其他项目。
3. **假如** 用户执行 `/project current`，**当** 当前路由已绑定项目时，**那么** 系统应返回绑定的项目 ID、名称、workspace 路径。

---

### 用户故事 2 - 同一 bot 并行多项目时保持隔离（优先级：P1）

作为 bot 使用者，我希望在同一 bot 下并行推进多个项目时，来自不同 channel/thread/peer 的消息可以稳定进入各自项目空间。

**为什么是这个优先级**: 这是“多项目并发”真实使用场景，直接决定是否可上线。

**独立测试方式**: 构造两个 route key（例如两个 Discord 线程），分别绑定不同项目并连续发送请求，验证 session、workspace、审计日志互相独立。

**验收场景**:

1. **假如** route key A 绑定 `project-a`，route key B 绑定 `project-b`，**当** 两边并行发送任务，**那么** 任务执行目录与会话索引必须严格分离。
2. **假如** A 路由执行 `/new`，**当** B 路由继续发送普通任务，**那么** B 路由当前会话与项目绑定不应被覆盖。
3. **假如** 某 route key 未绑定项目，**当** 消息到达时，**那么** 系统应回退到默认项目并记录“fallback”审计字段。

---

### 用户故事 3 - 意图识别辅助项目切换（优先级：P2）

作为用户，我希望系统在检测到“当前请求更像另一个项目”时给出切换建议，但不会静默切换，避免误判导致上下文错位。

**为什么是这个优先级**: 自动切换风险高，必须用“建议 + 确认”降低误切。

**独立测试方式**: 在 `project-a` 路由中发送明显属于 `project-b` 的请求，验证系统返回切换建议；确认后切换生效，拒绝则保持原项目。

**验收场景**:

1. **假如** 意图匹配到非当前项目且置信度高，**当** 用户请求到达时，**那么** 系统应返回“建议切换”而不是直接切换。
2. **假如** 用户确认切换，**当** 在确认有效期内执行确认命令，**那么** 当前 route key 绑定应更新到目标项目。
3. **假如** 用户拒绝或超时未确认，**当** 后续请求继续进入系统，**那么** 仍应保持原项目绑定。

---

### 用户故事 4 - 项目隔离可观测且可恢复（优先级：P3）

作为运维负责人，我希望项目注册表、路由绑定和会话索引具备可审计、可恢复能力，这样故障时能快速定位并回滚。

**为什么是这个优先级**: 多项目体系会引入更多状态，缺少治理会导致高故障成本。

**独立测试方式**: 模拟绑定文件损坏和项目缺失，验证系统可给出明确错误并支持重建绑定。

**验收场景**:

1. **假如** `bindings.json` 中存在无效项目 ID，**当** 路由命中该绑定，**那么** 系统应返回可读错误并建议修复。
2. **假如** 项目目录缺失但 registry 仍存在，**当** 访问该项目时，**那么** 系统应支持重建目录或切换到其他项目。
3. **假如** 运维执行项目审计命令，**当** 命令完成时，**那么** 系统应输出项目数量、绑定数量、异常绑定数量。

---

### 边界场景

- 同一 `channel/peer` 下存在多个线程时，必须优先按 `thread_id` 区分路由绑定。
- 迁移旧数据（仅 `window_id` 语义）时，如何补齐 `project_id` 默认值。
- 删除项目时，如何阻止误删仍有活动绑定或活动会话的项目。
- 意图识别频繁误命中时，如何限流“切换建议”提示频率。
- 默认项目被禁用或损坏时，系统如何拒绝执行并给出恢复指引。

## 需求（必填）

### 功能需求

- **FR-001**: 系统必须引入“项目（Project）”一等概念，并维护项目注册表。
- **FR-002**: 每个项目必须映射到独立 workspace 目录（默认 `~/.clawx/workspaces/<project_id>`）。
- **FR-003**: 系统必须支持 `/project create <id>` 创建项目与 workspace。
- **FR-004**: 系统必须支持 `/project list` 查看项目列表及状态（active/inactive/broken）。
- **FR-005**: 系统必须支持 `/project use <id>` 将当前 route key 绑定到目标项目。
- **FR-006**: 系统必须支持 `/project current` 返回当前 route key 对应项目信息。
- **FR-007**: `/new` 必须只创建会话，不得创建/切换项目。
- **FR-008**: 路由键（route key）必须至少包含 `channel`、`instance`、`peer_kind`、`peer_id`，并在可用时包含 `thread_id`。
- **FR-009**: route key 必须优先使用显式线程维度，避免同频道多线程串项目。
- **FR-010**: 会话键必须纳入 `project_id` 维度，防止跨项目会话冲突。
- **FR-011**: 当 route key 无显式项目绑定时，系统必须回退到默认项目。
- **FR-012**: 默认项目必须可配置；未配置时使用 `main`。
- **FR-013**: 项目绑定存储必须与项目注册表分离，至少包含 `route_key`、`project_id`、`updated_at`、`updated_by`。
- **FR-014**: 系统必须提供 `/project bind <route_key> <project_id>` 与 `/project unbind <route_key>` 以支持运维修复。
- **FR-015**: 意图路由命中非当前项目时，系统必须输出“切换建议”并等待确认，不得静默切换。
- **FR-016**: 切换建议确认必须具备有效期（默认 10 分钟），超时后自动失效。
- **FR-017**: 项目切换、绑定变更、fallback 路由必须写入结构化审计日志。
- **FR-018**: 项目删除前必须检查活动绑定与活动会话，默认拒绝危险删除。
- **FR-019**: 项目相关存储文件必须支持原子写入，避免并发写坏。
- **FR-020**: 若项目 registry 与 workspace 目录不一致，系统必须标记 `broken` 并提供修复提示。
- **FR-021**: 本阶段不得改变 Phase 2 的窗口语义；项目选择应叠加在窗口语义之上。
- **FR-022**: 本阶段不得破坏现有 `/new`、`/resume`、`/list`、`/current`、`/switch`、`/cancel` 控制命令。
- **FR-023**: `clawx config` 需支持项目默认目录前缀配置（例如 `~/.clawx/workspaces`）。
- **FR-024**: 文档必须给出“同一 bot 并发两个项目”的目录与路由示例。

### 关键实体

- **项目（Project）**: 逻辑项目单元，持有 `project_id`、名称、workspace 路径与状态。
- **项目注册表（Project Registry）**: 所有项目的元数据索引。
- **路由绑定（Route Binding）**: `route_key -> project_id` 的映射关系。
- **项目会话键（Project Session Key）**: 含 `project_id` 的会话索引键。
- **切换建议（Project Switch Proposal）**: 意图识别生成的待确认切换记录。

### 假设

- Phase 2 窗口能力与 Phase 4 多渠道能力已可用。
- 初期采用本地文件持久化（`~/.clawx`），暂不引入数据库。
- 项目隔离以“工作目录 + 会话索引 + 路由绑定”三层为最小闭环。
- 本阶段先支持单节点部署，不覆盖跨节点一致性。

## 成功标准（必填）

### 可度量结果

- **SC-001**: 95% 以上的跨项目并行请求可命中正确项目 workspace，且无串线。
- **SC-002**: 100% 的 `/new` 请求不会隐式创建或切换项目。
- **SC-003**: 95% 以上的 `/project use` 后首条请求可在一次交互内命中目标项目。
- **SC-004**: 100% 的意图切换场景必须走“建议 + 确认”流程，不允许静默切换。
- **SC-005**: 项目绑定与注册表文件写入失败时，100% 返回可追踪错误，不得静默吞错。
- **SC-006**: route key 解析与项目判定（不含后端执行）p95 < 120ms。

### 统计口径

- 统计窗口：7 天滚动窗口，按候选发布批次统计。
- 样本量下限：每项成功标准不少于 200 次有效请求。
- 采集来源：集成测试日志、审计日志、人工验收脚本。
- 判定规则：任一 SC 未达标不得进入发布候选。
