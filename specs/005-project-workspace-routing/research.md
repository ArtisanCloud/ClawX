# 研究记录：项目空间隔离与路由

## 决策 1：`/new` 与 `/project` 明确分离
- **决策**: `/new` 仅创建会话；项目创建/切换只走 `/project` 命令或确认式切换。
- **理由**: 避免“新会话”与“新项目”语义混淆，减少误操作。
- **备选方案**:
  - `/new --project xxx`：灵活但会让控制命令复杂化。
  - `/new` 自动建项目：不可控，容易污染目录。

## 决策 2：route key 采用 `channel+instance+peer(+thread)` 组合
- **决策**: route key 最小字段为 `channel`、`instance`、`peer_kind`、`peer_id`；有线程时追加 `thread_id`。
- **理由**: 能覆盖 DM、群、线程三类场景，且与多渠道模型一致。
- **备选方案**:
  - 仅 `conversation_id`：跨渠道可解释性弱，排障困难。
  - 强制包含线程：无线程渠道无法统一。

## 决策 3：同一 main agent 可承载多项目，但 workspace 必须分离
- **决策**: 一个 agent 下可绑定多个项目，执行目录始终取 `project.workspace`。
- **理由**: 维持“agent 作为模板”的轻量策略，同时获得项目级隔离。
- **备选方案**:
  - 每项目一个 agent：隔离强但管理成本高。
  - 单 workspace 多项目目录：边界弱，容易串改。

## 决策 4：项目状态拆成 registry 与 bindings 两份文件
- **决策**: `projects.json` 管项目元数据，`bindings.json` 管 route key 绑定。
- **理由**: 降低写冲突与恢复复杂度，支持局部修复。
- **备选方案**:
  - 单文件全量存储：实现简单，但并发写风险更大。

## 决策 5：意图识别只做“建议切换”，不做自动切换
- **决策**: 命中非当前项目时生成 proposal，用户确认后才切换。
- **理由**: 项目切换是高影响动作，必须可控且可审计。
- **备选方案**:
  - 高置信自动切换：效率高但误切代价高。
  - 完全不做建议：安全但体验差。

## 决策 6：默认项目回退保留，但必须有审计字段
- **决策**: 无绑定时回退默认项目 `main`，同时记录 `routing_mode=fallback`。
- **理由**: 保证可用性，不阻塞旧路径；同时保留可观测性。
- **备选方案**:
  - 无绑定即报错：更严格但会影响存量入口。

## 决策 7：项目删除默认安全模式
- **决策**: 若存在活动绑定或活动会话，`/project delete` 默认拒绝。
- **理由**: 防止删除后出现大量悬挂路由与会话。
- **备选方案**:
  - 强制删除默认开启：风险高，仅适合运维手工恢复场景。
