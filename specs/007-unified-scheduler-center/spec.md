# 功能规格说明：Unified Scheduler Center（统一定时任务中心）

**功能分支**: `007-unified-scheduler-center`  
**创建时间**: 2026-03-17  
**状态**: 草稿  
**输入**: 用户描述: "根据 docs/plans/feature/007-unified-scheduler-center/plan.md 实现对应的 spec 开发文档。"

## 用户场景与测试（必填）

### 用户故事 1 - 统一注册与管理定时任务（优先级：P1）

作为 ClawX 使用者，我希望在当前项目和当前 Agent 下统一创建、查看、暂停、恢复、删除定时任务，这样我可以集中治理自动化任务，不需要依赖外部脚本分散维护。

**为什么是这个优先级**: 没有统一任务管理入口，就无法建立后续“自然语言触发”和“自动清理”的能力基础。

**独立测试方式**: 在同一会话中完成“新增任务 -> 查询任务 -> 暂停 -> 恢复 -> 删除”，验证每一步状态变化可见且可回溯。

**验收场景**:

1. **假如** 用户在当前项目提交一个新的周期任务，**当** 创建成功后，**那么** 任务必须出现在任务列表中并显示下一次执行时间。
2. **假如** 任务处于运行中状态，**当** 用户暂停任务，**那么** 系统必须停止后续自动触发并将状态更新为暂停。
3. **假如** 任务处于暂停状态，**当** 用户恢复任务，**那么** 系统必须重新参与调度并重新计算下一次执行时间。
4. **假如** 用户删除任务，**当** 删除成功后，**那么** 任务不再出现在列表且不会再次被自动触发。

---

### 用户故事 2 - 自然语言注册图片清理任务（优先级：P1）

作为图片工具使用者，我希望直接说“每周清理图片记录”，系统就能自动注册对应的定时任务，这样我不用记具体命令也能完成自动治理。

**为什么是这个优先级**: 这是你提出的核心用例，直接决定“自然语言可操作”是否成立。

**独立测试方式**: 发送自然语言需求，验证系统创建出目标任务，并可被查询与立即执行。

**验收场景**:

1. **假如** 用户发送“每周清理图片记录”，**当** 意图识别成功，**那么** 系统必须创建一条图片清理周期任务并返回可识别的任务标识。
2. **假如** 用户随后查询定时任务状态，**当** 系统返回列表时，**那么** 必须能看到该图片清理任务及其当前状态。
3. **假如** 用户要求立即执行该清理任务，**当** 执行完成后，**那么** 系统必须返回执行结果与清理摘要。

---

### 用户故事 3 - 多项目与多 Agent 隔离（优先级：P2）

作为平台管理员，我希望定时任务按项目和 Agent 隔离，避免不同项目或不同 Agent 的任务互相可见或互相影响。

**为什么是这个优先级**: 隔离是平台级安全边界；没有隔离会导致误操作和跨域污染。

**独立测试方式**: 在两个项目或两个 Agent 下分别创建同名任务，验证列表与执行只作用于各自作用域。

**验收场景**:

1. **假如** Project A 和 Project B 各自有任务，**当** 在 Project A 查询任务时，**那么** 不得返回 Project B 的任务。
2. **假如** 同一项目下 Agent X 与 Agent Y 各自有任务，**当** Agent X 执行查询或执行任务时，**那么** 不得读取或触发 Agent Y 的私有任务。

---

### 用户故事 4 - 统一可观测与恢复（优先级：P2）

作为运维人员，我希望查看每个任务最近执行时间、执行状态、失败原因，并在服务重启后自动恢复调度，这样我可以持续运维而不丢任务。

**为什么是这个优先级**: 定时系统若不可观测和不可恢复，线上问题难排查，且会造成任务漏执行。

**独立测试方式**: 触发一次成功执行与一次失败执行，再重启服务，验证历史可查且重启后继续调度。

**验收场景**:

1. **假如** 任务执行失败，**当** 用户查询任务状态，**那么** 系统必须展示最近失败时间和失败原因。
2. **假如** 服务发生重启，**当** 服务恢复后，**那么** 既有任务定义必须继续生效并按计划执行。

---

### 边界场景

- 当用户重复创建同名任务时，系统如何避免冲突并给出明确反馈。
- 当用户提供非法周期表达时，系统如何拒绝创建并给出可理解错误提示。
- 当任务执行时间超过一个调度周期时，系统如何避免并发重复执行。
- 当任务执行动作不可用或权限不足时，系统如何记录失败并避免阻塞其他任务。
- 当任务数量达到高并发规模时，系统如何保证查询和调度仍在可接受时延内。

## 需求（必填）

### 澄清决议（2026-03-17）

- 默认任务作用域：`project + agent`（可选扩展 route 绑定）。
- 自然语言“每周清理图片记录”默认执行时间：每周日 03:00（默认按 UTC 解释，可由项目配置覆盖）。
- 图片清理默认保留策略：保留最近 30 天。
- 任务失败默认策略：本次标记失败，等待下一个周期再执行。

### 功能需求

- **FR-001**: 系统必须提供统一的定时任务管理能力，支持新增、查询、暂停、恢复、删除与立即执行。
- **FR-002**: 系统必须为每个任务保存任务标识、任务名称、调度规则、任务类型、任务参数和状态。
- **FR-003**: 系统必须在任务新增或状态变更后，返回用户可识别且可追踪的结果。
- **FR-004**: 系统必须支持将明确自然语言指令映射为定时任务管理动作。
- **FR-005**: 系统必须支持“每周清理图片记录”自然语言触发创建图片清理周期任务（使用默认策略或用户显式参数）。
- **FR-006**: 系统必须对任务作用域执行隔离，默认覆盖 `project + agent`，并支持可选 route 级扩展。
- **FR-007**: 系统必须保证不同作用域的任务不可互查、不可互改、不可互执行。
- **FR-008**: 系统必须记录每次任务执行的开始时间、结束时间、执行状态与结果摘要。
- **FR-009**: 系统必须记录任务失败原因，供用户后续查询与排障。
- **FR-010**: 系统必须在服务重启后恢复任务定义并继续参与调度。
- **FR-011**: 系统必须保证单个任务在同一时刻最多只有一个活动执行实例。
- **FR-012**: 系统必须支持用户查询任务列表并看到当前状态、最近执行结果和下次计划执行时间。
- **FR-013**: 系统必须对非法调度规则、无效参数、任务冲突提供明确且可行动的错误反馈。
- **FR-014**: 系统不得因单个任务失败而影响其他任务的调度与执行。
- **FR-015**: 系统必须允许用户在不依赖外部系统任务编排器的前提下完成常见定时治理。
- **FR-016**: 系统必须对作用域变更（如 route 级绑定）提供显式声明与审计记录，避免隐式漂移。
- **FR-017**: 系统必须将“每周清理图片记录”映射为每周日 03:00 执行的周期任务（用户未指定时间时，按平台默认时区解释）。
- **FR-018**: 系统必须为图片清理任务提供默认“保留最近 30 天”的策略（用户未指定保留期时）。
- **FR-019**: 系统必须在任务单次执行失败后记录失败并保留任务启用状态，等待下一周期自动重试。

### 关键实体（如涉及数据）

- **定时任务（Schedule Job）**: 描述一个可被周期触发的自动化任务，包含名称、作用域、调度规则、类型、参数、状态与下一次执行时间。
- **任务作用域（Schedule Scope）**: 定义任务所属边界，至少包含项目标识与 Agent 标识，可扩展会话路由维度。
- **任务执行记录（Schedule Run Record）**: 记录某次实际执行的生命周期，包括开始/结束时间、执行结果、错误信息与摘要。
- **任务模板意图（Schedule Intent Template）**: 用于将自然语言意图映射为标准任务定义的规则模板。

### 假设

- 当前部署以单节点进程为主，统一调度由同一服务实例负责。
- 定时任务主要面向“平台内治理任务”和“工具维护任务”，不包含外部高风险自动化动作。
- 用户在发起自然语言请求时已处于明确项目上下文。
- 图片清理策略采用“保留最近 30 天”的默认业务规则（可被显式覆盖）。
- 默认时区采用 UTC；项目若配置业务时区，则以项目时区优先。

## 成功标准（必填）

### 可度量结果

- **SC-001**: 90% 以上的目标用户可在 2 分钟内完成首次“新增并查询”定时任务。
- **SC-002**: 100% 的跨项目与跨 Agent 访问测试中，不出现任务越权可见或越权执行。
- **SC-003**: 95% 以上的周期触发任务在计划时间后 1 分钟内开始执行。
- **SC-004**: 100% 的任务执行都可查询到最近一次执行状态与失败原因（如有失败）。
- **SC-005**: 服务重启后，100% 的已存在有效任务可在恢复后继续参与调度。
- **SC-006**: 对“每周清理图片记录”自然语言输入，意图到任务创建成功率达到 95% 以上。
