## Clarifications

### Session 2026-03-18

- Q: 当一条消息同时包含“配置意图”和“任务意图”时，系统应优先怎么处理？ → A: 先澄清：先询问“改配置还是执行任务”。
- Q: 当系统识别到“可能是配置意图”但置信度不足时，默认动作是什么？ → A: 不修改计划，只返回建议提示。
- Q: pending plan 的隔离粒度选哪种？ → A: 会话级隔离（channel + instance + conversation）。
- Q: pending plan 的补丁历史保留策略选哪种？ → A: 会话内完整保留直到 apply/cancel，并写入审计摘要。
- Q: 非管理员在配置控制面允许到哪一步？ → A: 可创建/编辑/查看计划，但不可 apply。

## 用户场景与测试（必填）

### 用户故事 1 - 自然语言与指令统一进入配置计划（优先级：P1）

作为频道管理员，我希望无论我输入 `/config plan ...` 还是自然语言“创建一个招投标 agent”，系统都进入同一个待确认配置计划，这样我不需要记忆两套行为模型。

**为什么是这个优先级**: 这是“体验连贯性”的核心问题，不解决就会持续出现“上一句可配、下一句断裂”的体验。

**独立测试方式**: 在同一会话中分别用指令与自然语言发起创建 Agent，验证两者都生成同一类 pending plan 并可通过 `/config show` 查看。

**验收场景**:

1. **假如** 用户发送 `/config plan 创建 agent bid-all`，**当** 系统解析成功时，**那么** 应生成待确认计划并提示 `/config apply`。
2. **假如** 用户发送“帮我新建一个 bid-all 智能体”，**当** 系统识别为配置意图时，**那么** 应生成同样结构的待确认计划而非进入普通执行回复。
3. **假如** 用户发送 `/config show`，**当** 当前会话已有 pending plan，**那么** 系统应返回结构化计划摘要及来源信息。

---

### 用户故事 2 - 自然语言可编辑已有计划（优先级：P1）

作为管理员，我希望在 `apply` 前用自然语言修改计划（例如“把 workspace 改成 bid-all”），这样我可以快速迭代配置而不必反复重建计划。

**为什么是这个优先级**: 这是修复“上下文不贯通”的直接能力，决定计划模式是否真正可用。

**独立测试方式**: 先创建 pending plan，再发送自然语言 patch，检查 `/config show` 是否反映新值，最后 `apply` 验证写盘结果一致。

**验收场景**:

1. **假如** 会话中已有 pending plan，**当** 用户发送“把 workspace 改成 /home/ubuntu/.clawx/workspaces/bid-all”，**那么** 系统应更新计划字段并记录变更。
2. **假如** 会话中没有 pending plan，**当** 用户发送“把 timeout 改成 900”，**那么** 系统应返回“当前无可编辑计划”的明确信息。
3. **假如** 用户连续两次 patch 同一字段，**当** 用户执行 `/config show`，**那么** 应展示最终值与变更轨迹摘要。

---

### 用户故事 3 - 所有配置落盘都走确认与权限治理（优先级：P1）

作为系统所有者，我希望任何配置写入都必须经过 `show -> apply` 且受权限约束，这样自然语言能力增强后也不会放大误操作风险。

**为什么是这个优先级**: 这是安全与治理底线，必须在体验增强前固化。

**独立测试方式**: 分别用管理员与非管理员账号执行 `apply`，验证权限差异；验证未 `apply` 前不会落盘。

**验收场景**:

1. **假如** 用户仅生成或修改了 plan，**当** 未执行 `/config apply`，**那么** 配置文件不得发生变更。
2. **假如** 非管理员执行 `/config apply`，**当** 权限校验触发时，**那么** 系统应拒绝写盘并返回权限提示。
3. **假如** 管理员执行 `/config apply`，**当** 执行成功时，**那么** 系统应返回写入成功与重启提示。

---

### 用户故事 4 - 配置意图链路可审计、可追踪（优先级：P2）

作为运维与审计人员，我希望知道配置计划来自哪里、被谁修改、最终写入了什么，这样出现配置异常时可以快速回溯责任和过程。

**为什么是这个优先级**: 统一控制面若不可观测，会导致问题定位困难并增加运营风险。

**独立测试方式**: 完整走一次“创建计划 -> patch -> apply”，检查日志与审计输出是否包含来源、操作者、差异摘要。

**验收场景**:

1. **假如** 计划由自然语言触发，**当** 系统记录计划事件时，**那么** 审计信息应标记来源为自然语言。
2. **假如** 计划由指令触发，**当** 系统记录计划事件时，**那么** 审计信息应标记来源为指令。
3. **假如** 同一计划经历多次 patch，**当** 执行 apply 后，**那么** 审计信息应包含最终变更摘要与操作者。

---

### 边界场景

- 用户消息同时包含任务意图与配置意图时，系统如何避免误入错误通道。
- 自然语言 patch 指向非法值（如空 Agent ID、非法超时）时，系统如何拒绝并给出可行动提示。
- 同一会话内并发触发多个配置请求时，系统如何避免 pending plan 被覆盖。
- 低置信度语义识别时，系统如何降级为“建议确认”而非直接修改计划。
- 用户切换会话窗口后，系统如何保证 pending plan 隔离，不串会话。

## 需求（必填）

### 功能需求

- **FR-001**: 系统必须支持通过斜杠指令和自然语言两种入口创建配置计划。
- **FR-002**: 两种入口生成的计划必须使用同一结构与同一会话级存储，不得分叉。
- **FR-003**: 系统必须支持对当前 pending plan 进行自然语言补丁修改（至少覆盖 Agent、workspace、profile、timeout、default）。
- **FR-004**: 当会话无 pending plan 时，系统必须拒绝补丁操作并返回明确提示。
- **FR-005**: 系统必须支持 `/config show` 展示当前会话 pending plan 的结构化摘要。
- **FR-006**: 系统必须支持 `/config cancel` 清空当前会话 pending plan。
- **FR-007**: 系统必须保证只有 `/config apply` 可以触发配置写入。
- **FR-008**: 系统必须在 `apply` 前保持配置文件不变，禁止隐式写盘。
- **FR-009**: 系统必须对 `apply` 执行权限校验，并在权限不足时拒绝操作。
- **FR-010**: 系统必须为每次计划创建、补丁、取消、应用记录可审计事件。
- **FR-011**: 审计事件必须至少包含会话标识、操作者、操作类型、计划来源、时间戳与变更摘要。
- **FR-012**: 系统必须支持配置意图识别失败时回退原有任务执行链路，不得影响普通任务可用性。
- **FR-013**: 系统必须在配置意图低置信度场景下采用保守策略（不写盘、不隐式改计划）。
- **FR-014**: 系统必须支持同一会话内多次补丁并保证最终展示值与应用值一致。
- **FR-015**: 系统必须在跨会话范围隔离 pending plan，避免不同会话互相读取或覆盖。
- **FR-016**: 系统必须为用户返回可理解的错误语义（如“无待编辑计划”“参数无效”“权限不足”“未确认不可执行”）。
- **FR-017**: 系统必须保持现有 `/agent` 与 `/config` 已有基础能力可用，不因本功能回退。
- **FR-018**: 当同一消息同时命中配置意图和任务意图时，系统必须先进入澄清流程，再根据用户确认进入对应通道。
- **FR-019**: 当配置意图识别置信度不足时，系统必须采用“建议提示”策略，不得自动修改 pending plan。
- **FR-020**: pending plan 的作用域必须固定为 `channel + instance + conversation`。
- **FR-021**: 系统必须完整保留会话内 patch 历史，直到 `/config apply` 或 `/config cancel` 后结束该计划生命周期。
- **FR-022**: 非管理员必须允许执行计划创建、编辑、查看、取消；但必须禁止执行 `/config apply`。
- **FR-023**: 系统必须提供控制面上下文压缩机制：将 pending plan 的 patch 历史维护为结构化摘要（非自由文本），并随计划版本更新。
- **FR-024**: `/config show` 必须同时展示“当前计划快照 + 压缩摘要 + 最近 N 条 patch 轨迹（可配置）”。
- **FR-025**: 配置意图判定在同会话多轮交互中必须可读取压缩摘要上下文，避免重复误判与上下文断裂。
- **FR-026**: 当压缩摘要与原始 patch 历史不一致时，系统必须以原始 patch 历史为准并标记摘要失效后重建。
- **FR-027**: 压缩摘要必须纳入审计事件（摘要版本/摘要来源/重建原因），支持事后回放。

### 关键实体（如涉及数据）

- **配置计划（Config Plan）**: 待确认的配置变更对象，包含目标 Agent 及可变字段。
- **计划补丁（Plan Patch）**: 针对配置计划的单次字段变更描述，记录来源与操作时间。
- **计划存储（Pending Plan Store）**: 按会话维度保存当前待确认计划及补丁历史。
- **配置意图决策（Config Intent Decision）**: 对输入消息的判定结果，表明是否进入配置控制面。
- **配置审计事件（Config Audit Event）**: 记录配置计划生命周期关键动作的追踪信息。
- **控制面摘要（Control-Plane Summary）**: 针对 pending plan 历史的结构化压缩视图，包含字段最终值、最近修改人、最近修改时间、patch 数量与摘要版本。

### 假设

- 当前系统已有 `/config plan/show/apply/cancel` 基础能力可复用。
- 配置写入仍以本地配置文件为权威来源。
- 管理员权限模型沿用现有配置指令权限机制。
- 本阶段以单实例部署为主，不要求跨节点一致性协议。

## 成功标准（必填）

### 可度量结果

- **SC-001**: 在“创建计划后再自然语言修改”的场景中，95% 以上请求可正确更新 pending plan。
- **SC-002**: 100% 的配置写入均通过 `/config apply` 触发，不出现隐式写盘。
- **SC-003**: 普通任务请求在未命中配置意图时，路由可用性保持 99% 以上且不受明显回归影响。
- **SC-004**: 管理员与非管理员权限边界准确率达到 100%（非管理员不得 apply 成功）。
- **SC-005**: 配置计划关键事件审计覆盖率达到 100%（创建、补丁、取消、应用）。
- **SC-006**: 同一会话内从计划创建到应用完成的交互步骤中位数不高于 4 步。
- **SC-007**: 在包含 20 次以上 patch 的会话中，`/config show` 仍能在 500ms 内返回压缩摘要与最近轨迹（本地单实例基线）。
- **SC-008**: 压缩摘要与最终应用配置的一致性达到 100%（抽样回放验证）。
