# Analyze：013 Lead/Worker Runtime Orchestrator

## 1. 问题复盘

当前痛点不是“能不能执行命令”，而是“执行模型不稳定”：
- 主 Agent 与执行 Agent 职责混杂，用户难以理解当前谁在干活。
- 任务推进缺少显式调度层，导致“走一步汇报一步”与模板化回执。
- 会话中断后缺少统一任务账本，恢复依赖临时上下文，连续性差。
- Spec Kit 流程虽可执行，但缺少会话级状态继承，容易误触发门禁。

## 2. 方案选择

### 方案 A：继续在现有执行链上打补丁
- 优点：改动小、上线快。
- 缺点：架构边界继续模糊，后续复杂度持续增长。
- 结论：不推荐作为长期方案。

### 方案 B：引入 Lead/Worker Runtime Orchestrator（推荐）
- 优点：
  - 职责边界清晰（Lead 调度，Worker 执行）
  - 任务与状态可持久化、可恢复、可审计
  - 与 Spec Kit 门禁天然兼容（先规范后实现）
- 风险：
  - 初期改动面较大，需要分阶段交付
  - 需要补齐回归测试，避免影响现有路径

## 3. 关键决策

1. 保持现有 `action_plan` 协议，不新增第二套执行协议。  
2. Runtime 状态按 agent workspace 隔离，避免跨 agent 污染。  
3. “启动”作为自然语言入口，触发 bootstrap 流程。  
4. 规范场景沿用 Spec Kit 四件套完整性门禁。  
5. 用户侧回执固定为“结论/产物/证据/下一步”。

## 4. 不做项（本期）

- 不做跨机分布式 worker 调度（仅单机 workspace 范围）。
- 不做完整 Web 可视化调度面板（先做日志与 CLI 可观测）。
- 不做任意自动扩缩容策略（先支持固定 worker 池）。

## 5. 技术验证清单

- [ ] 启动 bootstrap 后状态文件可重复初始化且幂等
- [ ] Worker 心跳超时判定不会误杀 busy worker
- [ ] 任务回收重派不出现重复执行
- [ ] Spec Kit 缺项时给出明确缺失文件和下一步动作
- [ ] “继续补齐”在会话内稳定续流，不误触发实现门禁

## 6. 交付门禁

- Gate 1：`spec.md/plan.md/tasks.md/analyze.md` 四件套完整。
- Gate 2：P1 任务完成后才能开放默认自动调度。
- Gate 3：`go test ./... -count=1` 全绿。
- Gate 4：至少 1 条真实对话链路验证“启动 -> 调度 -> 恢复 -> 回执”闭环。
