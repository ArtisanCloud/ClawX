# 研究记录：Skill Registry 与意图路由

## 决策 1：Skill 格式完全兼容 Claude Code `SKILL.md`
- **决策**: Skill 目录以 `SKILL.md` 为唯一必需入口，frontmatter 至少包含 `name`、`description`。
- **理由**: 目标是直接复用现有 Skill 生态，避免 ClawX 自建格式导致迁移成本。
- **备选方案**:
  - 定义 ClawX 私有 manifest：灵活但破坏兼容目标。
  - 双格式并存：实现复杂度更高且长期维护成本大。

## 决策 2：Skill 来源采用固定优先级
- **决策**: 来源优先级为 `~/.clawx/skills` > `<workspace>/.clawx/skills` > 内置。
- **理由**: 让用户级覆盖与项目级覆盖行为可预测，冲突处理可解释。
- **备选方案**:
  - 仅按最后加载覆盖：顺序不稳定，排障困难。
  - 全部并存并随机命中：不可接受。

## 决策 3：同名 Skill 冲突采用“单激活 + shadowed”
- **决策**: 同名冲突时仅激活一个条目，其余标记 `shadowed` 并记录告警。
- **理由**: 保证运行时行为确定性，同时保留可观测性。
- **备选方案**:
  - 全拒绝：安全但可用性差。
  - 静默覆盖：行为不可追踪。

## 决策 4：意图路由采用“规则优先 + LLM 兜底”
- **决策**: 路由优先级固定为：控制命令 > 显式 `/skill` > 精确名匹配 > 别名匹配 > LLM 兜底 > 普通任务。
- **理由**: 在可控性与灵活性之间取得平衡，并与现有控制命令语义兼容。
- **备选方案**:
  - 全 LLM：不可解释且误判风险高。
  - 纯规则：自然语言意图覆盖不足。

## 决策 5：多候选命中时自动选择，不进行二次询问
- **决策**: 多候选场景按固定优先级自动选择单一 Skill，禁止让用户二次选择。
- **理由**: 群聊和移动端场景中二次交互成本高，且用户已明确不接受此交互方式。
- **备选方案**:
  - 返回候选让用户选：体验冗长，违背确认结论。
  - 全量回退普通任务：会损失 Skill 命中价值。

## 决策 6：默认权限采用“频道白名单 + DM pairing”
- **决策**: 未显式授权配置时，Skill 使用默认遵循频道白名单与 DM pairing。
- **理由**: 与当前渠道安全基线和参考实现策略一致，适合逐步放量。
- **备选方案**:
  - 默认全开：风险不可控。
  - 默认仅管理员：过于保守，影响可用性。

## 决策 7：Skill 刷新采用“运行中可刷新 + 新请求生效”
- **决策**: 支持运行中刷新 Skill 索引，对刷新后的新请求立即生效；不强制中断已有执行。
- **理由**: 满足运维可操作性，避免重启服务带来的中断。
- **备选方案**:
  - 仅启动时加载：变更反馈慢。
  - 刷新时中断所有会话：影响会话稳定性。

## 决策 8：路由审计日志标准化
- **决策**: 每次路由记录 `intent.kind`、`intent.reason`、`intent.skill_name`、`intent.confidence` 等字段。
- **理由**: 误判排障依赖可追溯日志，没有日志会导致线上不可运维。
- **备选方案**:
  - 仅记录最终输出：无法定位路由错误来源。
  - 记录过多原文细节：增加敏感信息暴露风险。
