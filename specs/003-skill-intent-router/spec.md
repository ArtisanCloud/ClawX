## Clarifications

### Session 2026-03-08

- Q: 意图兜底策略默认值怎么定？ → A: 默认开启“规则优先 + LLM 兜底”，低置信度回退普通任务。
- Q: 同名 Skill 冲突时如何处理？ → A: 按来源优先级激活一个，其余标记为 `shadowed` 并告警。
- Q: 未配置白名单时，默认权限怎么定？ → A: 采用“频道白名单 + DM 配对（pairing）”默认策略。
- Q: 当一条消息同时命中多个 Skill 候选时，系统默认怎么处理？ → A: 自动选择最高优先级候选，不进行用户二次选择。
- Q: 自动选择的稳定规则怎么定？ → A: 先显式 `/skill`，再精确名匹配，再别名匹配，最后 LLM 最高置信度。

## 用户场景与测试（必填）

### 用户故事 1 - 可复用现有 Skill 资产（优先级：P1）

作为系统管理员，我希望平台可以直接识别并使用符合 Claude Code 规范的 Skill，这样我不需要为 ClawX 重新改造一套 Skill 内容，就能快速上线能力。

**为什么是这个优先级**: 这是本功能的核心业务价值，决定了是否能复用现有生态，直接影响接入成本与上线速度。

**独立测试方式**: 准备一个符合规范的 Skill 目录后导入系统，确认可以被系统识别、展示，并可被后续路由流程引用。

**验收场景**:

1. **假如** 管理员提供了一个规范 Skill 目录，**当** 系统执行刷新后，**那么** 该 Skill 会出现在可用列表中。
2. **假如** Skill 内容缺失关键元信息，**当** 系统加载该 Skill，**那么** 系统会拒绝该 Skill 并给出明确原因。

---

### 用户故事 2 - 消息可被稳定路由到正确处理路径（优先级：P2）

作为频道中的使用者，我希望我的消息能被稳定分流到“控制命令、Skill 执行、普通任务”中的正确路径，避免误判导致执行结果不可预期。

**为什么是这个优先级**: Skill 可用之后，路由正确性决定了实际体验质量；误路由会直接造成错误执行和信任下降。

**独立测试方式**: 使用同一会话分别发送控制类消息、显式技能消息与普通自然语言请求，验证每类消息都进入预期路径。

**验收场景**:

1. **假如** 使用者发送的是会话控制命令，**当** 系统处理该消息，**那么** 系统应进入控制路径而非技能或普通任务路径。
2. **假如** 使用者明确请求某个可用 Skill，**当** 系统路由该消息，**那么** 系统应进入对应 Skill 处理路径。
3. **假如** 使用者发送普通任务描述且无明确 Skill 命中，**当** 系统处理该消息，**那么** 系统应进入普通任务路径。

---

### 用户故事 3 - Skill 使用受权限与治理约束（优先级：P3）

作为运维负责人，我希望可以按频道、用户和技能开关控制 Skill 使用范围，这样可以在生产环境中逐步放量并降低误用风险。

**为什么是这个优先级**: 治理能力是上线前置条件。没有授权边界，Skill 会带来不可控风险。

**独立测试方式**: 配置不同权限组合，在授权与未授权用户/频道下分别触发同一 Skill，验证行为符合配置策略。

**验收场景**:

1. **假如** 某用户未在授权范围，**当** 其尝试触发 Skill，**那么** 系统应拒绝并给出可理解提示。
2. **假如** 某 Skill 被禁用，**当** 任何用户请求该 Skill，**那么** 系统应统一拒绝并提示该 Skill 当前不可用。

---

### 边界场景

- 当多个 Skill 语义相近并可能同时匹配时，系统如何保证选择结果稳定且可解释。
- 当系统未识别到明确 Skill 意图时，系统如何安全回退到普通任务路径而非误触发技能。
- 当 Skill 在运行中被禁用或刷新时，系统如何处理正在执行与后续请求的一致性。
- 当同名 Skill 出现在多个来源时，系统如何确定唯一生效项并对被遮蔽项给出可观测状态。
- 当单条消息命中多个候选 Skill 时，系统必须按固定优先级自动选择，且不得要求用户二次选择。
- 当 LLM 兜底置信度接近阈值时，系统如何保证回退行为一致且可配置。
- 当 DM pairing 过期或失效时，系统如何拒绝 Skill 调用并提示重新配对。

## 需求（必填）

### 功能需求

- **FR-001**: 系统必须支持加载符合 Claude Code 规范的 Skill，并可识别其基础元信息。
- **FR-002**: 系统必须支持对 Skill 执行可用性校验，并对无效 Skill 提供明确失败原因。
- **FR-003**: 系统必须提供可查询的 Skill 列表视图，至少包含可用、无效、禁用、被遮蔽等状态。
- **FR-004**: 系统必须将入站消息路由到三类处理路径：控制路径、Skill 路径、普通任务路径。
- **FR-005**: 系统必须保证控制命令优先级高于 Skill 与普通任务路径。
- **FR-006**: 系统必须支持显式指定 Skill 的调用方式，并保证显式请求优先于模糊匹配。
- **FR-007**: 系统必须默认采用“规则优先 + LLM 兜底”的意图判定策略，并在低置信度场景回退到普通任务路径。
- **FR-008**: 系统必须支持按用户范围、频道范围和 Skill 开关进行访问控制；未显式配置时按“频道白名单 + DM 配对”策略生效。
- **FR-009**: 系统必须记录每次路由决策的可追溯信息，便于排障与审计。
- **FR-010**: 系统必须在不破坏现有会话控制能力的前提下引入 Skill 路由能力。
- **FR-011**: 系统必须支持运行中刷新 Skill 清单，并在刷新后对新请求生效。
- **FR-012**: 系统必须对所有拒绝场景返回用户可理解的反馈，不得静默失败。
- **FR-013**: 系统必须对同名 Skill 执行确定性冲突处理：仅激活一个生效项，其他同名项标记为 `shadowed`，并提供可观测告警信息。
- **FR-014**: 当一条消息命中多个 Skill 候选时，系统必须自动选择单一候选继续处理，不得进入用户二次选择流程。
- **FR-015**: 自动选择流程必须遵循固定顺序：显式 `/skill` > 精确名匹配 > 别名匹配 > LLM 最高置信度。
- **FR-016**: 系统必须提供 LLM 兜底置信度阈值配置，且在未配置时使用明确默认值。
- **FR-017**: 系统必须定义并执行 DM pairing 生命周期规则（创建、有效期、失效、重配对）。
- **FR-018**: 系统必须对拒绝场景提供可区分的错误类别，至少覆盖权限不足、Skill 不存在、Skill 不可用、Skill 无效与配对失效。
- **FR-019**: 系统必须保持现有控制命令（`/new`、`/resume`、`/list`、`/cancel`）语义不回归。

### 关键实体（如涉及数据）

- **Skill 定义**: 一项可复用能力的描述实体，包含名称、用途描述与执行指令内容。
- **Skill 目录条目**: 系统当前可见的 Skill 记录，包含来源、状态与可见性信息。
- **路由决策**: 单条消息处理时产生的判定结果，包含目标路径、触发原因与置信信息。
- **授权规则**: 定义哪些用户与频道可使用哪些 Skill 的治理规则集合。

### 假设

- 现有会话控制命令与频道收发链路已经可用并稳定运行。
- 本阶段默认以单次消息命中一个 Skill 为原则，不包含多 Skill 编排。
- 若无显式授权配置，系统采用“频道白名单 + DM 配对（pairing）”作为默认权限策略。
- 本阶段重点是“可复用 + 可路由 + 可治理”，不包含可视化管理界面。

## 成功标准（必填）

### 可度量结果

- **SC-001**: 90% 以上的规范 Skill 在一次刷新后可被系统正确识别并进入可用状态。
- **SC-002**: 95% 以上的控制命令消息可被正确分流到控制路径，且不被误判为 Skill 请求。
- **SC-003**: 90% 以上的显式 Skill 请求可在一次交互内进入目标 Skill 路径并返回结果。
- **SC-004**: 100% 的未授权 Skill 请求会被拒绝并返回明确原因。
- **SC-005**: 95% 以上的路由执行可在日志中追踪到完整的“输入-判定-结果”链路信息。
- **SC-006**: 95% 以上的消息在不含后端执行时间的路由判定阶段可在 100ms 内完成。
- **SC-007**: 95% 以上的 Skill 刷新在 1 秒内对后续新请求生效。
