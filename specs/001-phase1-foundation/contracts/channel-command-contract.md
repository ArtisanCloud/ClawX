# 契约：渠道命令与消息归一化

## 目的
定义第一阶段中渠道输入如何映射为统一内部请求，以及系统如何返回统一输出语义。

## 1. 入站归一化消息结构

每个渠道适配器在进入核心链路前，必须将请求转换为以下统一结构：

```text
conversation_id
user_id
text
reply_to (可选)
attachments (可选)
channel
context_flags
```

### 字段说明
- `conversation_id`: 统一对话标识，必须可区分私聊和线程。
- `user_id`: 发起请求的用户标识。
- `text`: 用户输入内容，包含自然语言请求或控制命令。
- `reply_to`: 引用关系，可为空。
- `attachments`: 附件信息，可为空。
- `channel`: 当前渠道类型。
- `context_flags`: 用于表示是否私聊、是否线程、是否允许执行等上下文信息。

## 2. 控制命令集合

第一阶段统一支持以下控制命令：
- `/new`
- `/resume`
- `/list`
- `/cancel`

### 约束
- 两个受支持渠道的控制命令语义必须一致。
- 如果某个渠道存在语法差异，差异只允许存在于渠道适配层，不允许进入领域规则。

## 3. 自然语言请求

- 非控制命令文本默认视为执行请求。
- 执行请求进入 `Router` 后，必须先完成会话判定，再进入后端执行。

## 4. 出站输出契约

渠道适配器必须提供以下送达能力：
- `send_text(session, chunk, is_final)`
- `send_error(session, message)`

### 送达要求
- 输出片段必须保持顺序。
- 单片段长度必须符合渠道上限。
- 失败时必须按有限重试策略处理，并记录日志。
