# 研究记录：第一阶段基座能力

## 决策 1：核心运行模块使用 Go 1.23
- **决策**: 第一阶段核心运行模块使用 Go 1.23。
- **理由**: 宪章已明确 Go 为默认实现语言；Go 标准库适合实现并发控制、进程管理、结构化日志与长驻服务；同时与当前 Ubuntu 22.04 可稳定安装的系统包版本保持一致，便于后续 Linux 部署和运维。
- **备选方案**:
  - Python：脚本化快，但不符合当前 Go-first 宪章。
  - Node.js：与部分渠道生态兼容，但不符合当前默认语言策略。

## 决策 2：按 DDD 分层组织代码
- **决策**: 采用 `Domain / Application / Infrastructure / Interface` 四层结构。
- **理由**: 第一阶段虽然范围较小，但已经包含会话规则、执行约束、渠道接入与后端适配，若不在基座阶段分层，后续扩展多窗口、多会话时会快速耦合。
- **备选方案**:
  - 按技术类型平铺（handlers/services/utils）：实现快，但会把领域规则混入基础设施代码。
  - 单目录小项目：初期简单，但无法支撑后续阶段演进。

## 决策 3：Phase 1 使用内存态会话存储
- **决策**: 第一阶段使用内存态会话状态与锁管理。
- **理由**: 当前范围是验证最短执行链路，先降低持久化复杂度；运维与排障依然通过结构化日志和执行摘要补足。
- **备选方案**:
  - SQLite：可以更早持久化，但会提前引入迁移和并发细节。
  - Redis：超出第一阶段范围，且引入外部依赖。

## 决策 4：渠道接入采用单独适配器
- **决策**: Discord 与 Telegram 分别实现独立渠道适配器，但统一映射到同一内部消息结构。
- **理由**: 两个渠道的触发规则和消息长度限制不同，需要在边界层处理；统一内部结构能保证核心会话和执行逻辑不依赖渠道细节。
- **备选方案**:
  - 将渠道逻辑直接写入 Router：会让领域和交互逻辑耦合。
  - 完全抽象到一个超通用适配器：第一阶段收益不足。

## 决策 5：输出采用分段式稳定送达，而非强制真实流式
- **决策**: 第一阶段输出以稳定的分段送达为基线，若后端支持更细粒度流式，可在不改变用户语义的前提下增强。
- **理由**: 第一阶段重点是顺序、可读性和渠道限制，而不是追求最细的流式体验；分段式实现更容易保证正确性。
- **备选方案**:
  - 强制真实流式：复杂度更高，且与后端能力耦合。
  - 仅等待完整结果再返回：会降低可用性和可观察性。

## 决策 6：健康信号采用轻量健康探针
- **决策**: 第一阶段提供最小健康能力，只覆盖进程可用性与后端探针可达性。
- **理由**: 运维基线要求健康检查，但第一阶段不需要完整管理面板或复杂监控栈。
- **备选方案**:
  - 完整监控系统：超出第一阶段范围。
  - 无健康探针：不满足当前运维基线。
