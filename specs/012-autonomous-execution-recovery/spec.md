# 功能规格说明：Autonomous Execution & Recovery（自治执行与恢复）

**功能分支**: `012-autonomous-execution-recovery`  
**创建时间**: 2026-03-23  
**状态**: Draft  
**输入**: 用户要求“用通用方案提升 Agent 自主性，不是针对单一场景打补丁”。

## 用户场景与测试

### 用户故事 1 - 失败后自动自愈（P1）

作为使用者，我希望 Agent 在执行失败后先自动尝试恢复，而不是立刻把决策抛给我。

**验收场景**:
1. 执行失败后系统能给出结构化失败类型（如 network/permission/auth/tool/resource/unknown）。
2. 系统按失败类型自动执行恢复策略（有限重试与回退）。
3. 在可恢复场景下，用户不需要额外输入即可继续推进任务。

### 用户故事 2 - 最小打扰升级提问（P1）

作为使用者，我希望只有在确实需要我决策时才被问，并且问题包含已尝试证据和推荐选项。

**验收场景**:
1. 升级提问仅在高风险、缺凭据、预算冲突或策略冲突等场景触发。
2. 提问消息必须包含“已尝试步骤 + 失败原因 + 推荐下一步”。
3. 非必要场景不得频繁请求用户确认。

### 用户故事 3 - 可审计与可回放（P1）

作为运维，我希望自治决策过程可追溯，能明确每次恢复尝试发生了什么。

**验收场景**:
1. 每次自治链路记录 `classify -> attempts -> result -> escalation`。
2. 日志支持按 agent/channel/conversation 查询。
3. 失败后可回放关键动作与证据。

## 功能需求

- **FR-001**: 系统必须在执行失败后生成统一的 `FailureClass`。
- **FR-002**: 系统必须支持按 `FailureClass` 绑定 `RecoveryPolicy`。
- **FR-003**: 恢复策略必须支持有限重试，并采用默认参数：`max_retries=3`、指数退避 `1s/2s/4s`、单次恢复链路 hard timeout `<=30s`；命中熔断条件（如权限拒绝、凭据缺失）必须立即停止重试。
- **FR-004**: 系统必须支持恢复失败后的升级提问策略（最小打扰）。
- **FR-005**: 升级提问消息必须携带“已尝试清单、失败摘要、推荐动作”。
- **FR-006**: 系统必须将自治链路写入结构化审计日志。
- **FR-007**: 非 `/` 自然语言路径保持 LLM-first；`/command` 继续命令规则路径。
- **FR-008**: 自治层不得绕过既有 `control_plan` / `requirement_sync` schema 校验与 allowlist。
- **FR-009**: 用户响应默认简报模式（不自动贴长代码块、不自动回传附件，除非明确要求）。

## 关键实体

- **FailureClass**: 失败分类（network/auth/permission/resource/tool/unknown）。
- **RecoveryPolicy**: 恢复策略定义（步骤、重试、退避、终止条件）。
- **RecoveryAttempt**: 单次恢复尝试记录（动作、结果、耗时、证据）。
- **EscalationPrompt**: 升级提问结构（问题、推荐选项、上下文证据）。
- **AutonomyAuditRecord**: 自治审计记录（阶段、状态、关联会话）。

## 成功标准

- **SC-001**: 在 7 天滚动窗口内，对 `recoverable=true` 且 `FailureClass in {network, tool, resource}` 的样本，自动恢复成功率 `>=60%`。
- **SC-002**: 升级提问中，100% 包含已尝试证据与推荐动作。
- **SC-003**: 在 7 天滚动窗口内，用户侧“无效打扰提问”频次较基线下降 `>=30%`。
- **SC-004**: 自治日志完整率 100%（发生自治流程即有审计）。

## 与既有规格关系

- 与 `011-prompt-caching-staged-routing` 的关系：
  - 011 负责“分阶段结构化计划 + 缓存观测”；
  - 012 负责“执行失败后的自治恢复与升级提问”。
- 012 复用 011 的结构化输出，不重复定义 Planner/Route Planner 协议。
