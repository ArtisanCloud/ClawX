# 研究记录：第二阶段多窗口多会话

## 决策 1：窗口绑定采用显式关系，而不是只依赖 `Session.window_id`
- **决策**: 引入显式窗口绑定关系 `window_id -> current_session_id`，并把 `conversation_id` 作为兼容定位维度。
- **理由**: 仅依赖 `Session.window_id` 无法稳定表达“当前窗口当前会话指针”，尤其在同窗口切换、恢复、并行场景下容易语义混淆。
- **备选方案**:
  - 仅使用 `Session.window_id`：实现简单，但会让“当前指针”与“历史归属”耦合。
  - 完整新增独立 Window 服务：当前阶段复杂度过高。

## 决策 2：缺省 `window_id` 统一使用兼容值 `compat:<conversation_id>`
- **决策**: 当入口未显式传入 `window_id` 时，在归一化层生成 `compat:<conversation_id>`。
- **理由**: 兼容值可保持旧入口可用，同时把内部逻辑统一到窗口模型，避免 Phase 2 与 Phase 1 双路由长期并存。
- **备选方案**:
  - 缺省为空并在业务层兜底：分支过多，难以保证一致性。
  - 直接把 `conversation_id` 视为永久 `window_id`：会限制未来 Web/UI 多窗口扩展。

## 决策 3：纳入 `/switch <session_id>` 以消除 `resume` 语义歧义
- **决策**: 在 Phase 2 增加 `/switch`；`resume` 保留“恢复并绑定”，`switch` 仅切换指针不执行。
- **理由**: 若仅靠 `resume` 同时承担恢复与切换，会导致用户行为与状态更新难以解释，测试边界模糊。
- **备选方案**:
  - 不新增 `/switch`，全部由 `resume` 承担：文档和行为容易分叉。

## 决策 4：控制命令由 Core Router 优先解析
- **决策**: 内建命令 `/new`、`/resume`、`/list`、`/cancel`、`/current`、`/switch` 固定走 Core Router 分支。
- **理由**: 控制命令是会话安全边界的一部分，不能被技能或自然语言路由覆盖。
- **备选方案**:
  - 命令和技能共用同级匹配：会引入冲突与安全回退风险。

## 决策 5：窗口最近使用顺序在四类动作后刷新
- **决策**: `new`、`resume`、`switch`、执行成功后都刷新 `last_used_at`。
- **理由**: 用户心智中的“当前活跃会话”由操作行为驱动，而不仅是执行成功事件。
- **备选方案**:
  - 仅执行成功时刷新：切换后列表顺序会与用户预期不一致。

## 决策 6：窗口绑定更新沿用仓储锁语义，避免新增并发模型
- **决策**: 在现有仓储互斥基础上完成窗口绑定读写，不引入新并发框架。
- **理由**: 当前并发规模与复杂度可由现有锁模型覆盖，优先降低回归风险。
- **备选方案**:
  - 新增异步事件总线：超出本阶段范围。
