# 持久化策略（轻量优先）

## 背景
- 当前项目目标是先跑通渠道到执行器的最小闭环。
- 在这个阶段引入 PostgreSQL 会显著增加部署复杂度和排障成本。
- 因此持久化策略调整为：默认本地文件、可选增强，不把数据库作为前置依赖。

## 核心决策
1. 默认持久化方案：本地文件（`sessions.json + *.jsonl`）。
2. 第一阶段联调不强制数据库，优先保证链路可用。
3. 数据库能力改为可选扩展，不再作为 MVP 主路径。

## 当前实现现状（2026-03-06）
1. 默认会话仓储已切换为本地文件（无数据库依赖）。
2. PostgreSQL 仍然可选可用。
3. 文件仓储已支持 `sessions.json + *.jsonl` 的基础读写与重启恢复。

## 状态目录规范
所有状态统一落在 `~/.synapsex`：

```text
~/.synapsex/
  config.json
  workspaces/
    <agent_id>/
  agents/
    <agent_id>/
      sessions/
        sessions.json
        <session_id>.jsonl
  logs/
```

说明：
- `sessions.json` 保存会话索引和窗口绑定关系。
- `*.jsonl` 保存完整对话与执行转录，便于回放和审计。

## 数据分层
1. 运行态（内存）：
- 会话锁、当前执行状态、短生命周期缓存。

2. 持久态（文件）：
- 会话元数据、窗口当前会话指针、会话最近活跃时间。
- 每个会话的完整消息与执行转录（JSONL）。

3. 可选增强（后续）：
- SQLite 仅用于检索/统计索引，不作为主数据源。
- 外部数据库作为部署扩展能力，不在默认路径内。

## 写入一致性策略
1. `*.jsonl` 采用 append-only 写入。
2. `sessions.json` 采用“临时文件 + 原子替换（rename）”。
3. 任意写入失败时：
- 不回滚已存在转录文件。
- 记录错误日志，并在下次启动执行恢复扫描。

## 启动恢复策略
1. 启动先读取 `sessions.json`。
2. 若索引缺失或损坏：
- 从 `sessions/*.jsonl` 扫描重建最小索引。
3. 若发现索引存在但转录缺失：
- 将该会话标记为异常状态并记录告警，不阻塞服务启动。

## 生命周期与清理
1. 默认保留全部会话转录，不自动删除。
2. 提供手动清理命令（后续实现）：
- 按会话数量上限清理。
- 按最后活跃时间清理。
- 清理前输出 dry-run 结果。

## 分阶段落地
1. Phase 1（当前）
- 不依赖数据库完成主链路联调。
- 文档、测试和引导流程默认走轻量模式。
- 默认会话仓储：本地文件持久化。

2. Phase 2
- 完善文件仓储能力（清理、回放、恢复策略增强）。
- 将窗口绑定从内存态扩展为更完整的文件持久化模型。

3. Phase 3
- 多 Agent 下按 agent 目录隔离 session store。
- 增加会话回放、导出、清理能力。

4. Phase 4
- 评估并接入可选增强（如 SQLite 索引或外部数据库）。
- 不改变“本地文件为默认主存储”的原则。

## 验收标准
1. 服务重启后仍可 `/list` 找到历史会话。
2. `/resume <session_id>` 可恢复至重启前会话。
3. 会话转录文件可独立审计。
4. 无数据库依赖时，主链路可完整运行。
